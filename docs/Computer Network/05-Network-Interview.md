# 🧩 Network 面试题补充

本文补充一些原 Network 模块中较容易被追问、但常被答得不够完整的面试题。答题时建议遵循“概念 → 机制 → 场景 → 坑点”的顺序，既能覆盖基础，也方便面试官继续深挖。

## HTTP 与浏览器

### HTTP 是无状态协议，为什么还可以保持登录态？

HTTP 本身不会记住两次请求是不是来自同一个用户，但可以通过“客户端携带身份标识 + 服务端校验”的方式实现会话。

- **Cookie + Session**：服务端保存会话数据，客户端 Cookie 只保存 `session_id`，每次请求自动携带，服务端根据 `session_id` 找到登录状态。
- **Token/JWT**：服务端签发令牌，客户端通常放在 `Authorization: Bearer <token>` 中。服务端验证签名和过期时间后识别用户。
- **区别**：Session 更方便主动失效和集中管理，但需要服务端存储；JWT 更适合分布式和移动端，但令牌一旦签发，在过期前较难强制失效，通常需要黑名单或短 Access Token + Refresh Token。

### Cookie 的 `HttpOnly`、`Secure`、`SameSite` 分别解决什么问题？

- `HttpOnly`：禁止 JavaScript 读取 Cookie，主要降低 XSS 窃取 Cookie 的风险。
- `Secure`：只允许 Cookie 通过 HTTPS 发送，避免明文传输泄露。
- `SameSite`：限制跨站请求携带 Cookie，可缓解 CSRF。常见取值有 `Strict`、`Lax`、`None`，其中 `SameSite=None` 必须配合 `Secure`。

!!! note
    `HttpOnly` 不能防止浏览器自动携带 Cookie 发起请求，所以它不是 CSRF 的完整解决方案；CSRF 还需要 `SameSite`、CSRF Token、Referer/Origin 校验等手段。

### Session 和 JWT 怎么选？

- 单体应用、后台管理、强注销诉求明显：优先 Session，状态集中在服务端，踢人、封禁、权限变更更直接。
- 前后端分离、移动端、多服务共享身份：可以使用 Token/JWT，减少服务端会话存储压力。
- 安全实践：Access Token 有效期短，Refresh Token 有效期长但要可撤销；不要把敏感信息明文放进 JWT payload，因为它只是 Base64URL 编码，不是加密。

### GET 和 POST 的区别只在参数位置吗？

不是。更重要的是语义：

| 对比项 | GET | POST |
|---|---|---|
| 语义 | 获取资源 | 提交数据、创建资源或触发处理 |
| 安全性语义 | Safe，不应修改服务端状态 | 不保证 Safe |
| 幂等性 | 幂等 | 通常不幂等 |
| 缓存 | 更容易被缓存 | 默认不缓存 |
| 参数位置 | 常见于 URL Query | 常见于请求体 |

GET 技术上可以带 body，但兼容性和语义都不好，面试回答时建议说“规范没有绝对禁止，但实践中不建议依赖”。

### PUT、POST、PATCH 的区别是什么？

- `POST /users`：向资源集合提交数据，由服务端生成新资源，通常不幂等。
- `PUT /users/1`：完整替换指定资源，重复执行结果一致，通常幂等。
- `PATCH /users/1`：局部修改资源，是否幂等取决于接口设计。例如“把名字改为 Tom”是幂等，“余额增加 10”就不是幂等。

### 什么是幂等？为什么接口设计要关注幂等？

幂等指同一个请求执行一次和执行多次，对资源状态的影响相同。网络请求可能因为超时、重试、代理重放导致重复到达服务端，如果非幂等接口没有保护，可能造成重复下单、重复扣款。

常见方案：

- 使用唯一业务单号或幂等 Key。
- 服务端对请求状态去重。
- 数据库层使用唯一索引保证最终一致。

### HTTP 缓存完整流程是什么？

![HTTP 缓存决策流程](../Figures/Computer%20Network/HTTP缓存决策流程.svg)

HTTP 缓存先判断强缓存，再判断协商缓存：

- **强缓存命中**：浏览器直接使用本地缓存，不发请求。相关字段是 `Cache-Control` 和 `Expires`，其中 `Cache-Control` 优先级更高。
- **强缓存失效**：浏览器发起条件请求。常见请求头是 `If-None-Match`、`If-Modified-Since`。
- **协商缓存命中**：服务端返回 `304 Not Modified`，浏览器复用本地缓存。
- **协商缓存未命中**：服务端返回 `200 OK` 和新资源。

### `Cache-Control: no-cache` 和 `no-store` 有什么区别？

- `no-cache`：可以缓存，但每次使用前必须向服务端重新验证。
- `no-store`：完全不允许缓存，请求和响应内容都不应被存储，适合敏感数据。
- `max-age=3600`：资源在 3600 秒内可直接使用强缓存。
- `public` / `private`：控制是否允许共享缓存存储，例如 CDN 缓存通常关注 `public`。

### ETag 和 Last-Modified 有什么区别？

- `Last-Modified` 基于资源最后修改时间，精度通常到秒；如果一秒内多次修改，可能判断不准。
- `ETag` 是资源版本标识，可以基于内容 Hash、版本号等生成，更精确。
- 两者同时存在时，通常 `ETag / If-None-Match` 优先级更高。

### HTTP 长连接、管道化、多路复用有什么区别？

- **长连接**：同一个 TCP 连接可复用多个 HTTP 请求，减少重复握手成本。
- **HTTP/1.1 管道化**：多个请求可连续发出，但响应必须按顺序返回，仍有队头阻塞，浏览器实际支持有限。
- **HTTP/2 多路复用**：把请求和响应拆成二进制帧，通过 Stream ID 区分，多个流可交错传输，解决应用层队头阻塞。
- **HTTP/3 多路复用**：基于 QUIC，流之间更独立，进一步缓解 TCP 层丢包造成的队头阻塞。

### HTTP/2 为什么仍然可能队头阻塞？

HTTP/2 在应用层解决了 HTTP/1.1 响应必须排队的问题，但它仍跑在一条 TCP 连接上。TCP 要保证字节流有序交付，如果某个 TCP 包丢失，后续已经到达的数据也要等待重传后才能交给上层，因此整条连接上的多个 HTTP/2 Stream 都可能被影响。

### HTTP/3 为什么基于 UDP？

HTTP/3 使用 QUIC。QUIC 在 UDP 之上实现可靠传输、拥塞控制、流控制、TLS 1.3 加密和连接迁移。

核心收益：

- 减少握手延迟，支持 0-RTT 恢复连接。
- 多个 Stream 相互独立，某个流丢包不阻塞其他流。
- 使用 Connection ID 标识连接，移动网络切换 IP 后更容易保持连接。
- 加密和传输结合更紧密，中间设备更难篡改协议字段。

### HTTPS 一定安全吗？

不一定。HTTPS 解决的是传输链路上的机密性、完整性和身份认证，但仍可能被以下问题破坏：

- 用户忽略证书告警，信任了伪造证书。
- 设备被安装恶意根证书。
- 服务端 TLS 配置过旧，例如弱加密套件。
- 业务层有 XSS、CSRF、越权、SQL 注入等漏洞。

### TLS 1.2 和 TLS 1.3 的主要区别？

![TLS 1.3 握手流程](../Figures/Computer%20Network/TLS13握手流程.svg)

- TLS 1.3 删除了不安全或陈旧算法，如 RSA 静态密钥交换、RC4、SHA-1 等。
- TLS 1.3 主握手通常 1-RTT 完成，TLS 1.2 常见流程需要 2-RTT。
- TLS 1.3 支持 0-RTT 恢复，但 0-RTT 存在重放风险，不适合支付、下单等非幂等请求。
- TLS 1.3 更多握手内容被加密，减少中间人可观察的信息。

### 数字证书如何证明服务器身份？

证书由 CA 签发，包含域名、主体信息、公钥、有效期、签名算法等。客户端校验证书时会检查：

- 证书是否在有效期内。
- 访问域名是否匹配证书的 `Subject Alternative Name`。
- 证书链能否追溯到操作系统或浏览器信任的根 CA。
- 证书是否被吊销。
- 服务端是否持有证书对应的私钥，TLS 握手中的签名过程会证明这一点。

### CORS 是什么？简单请求和预检请求有什么区别？

CORS 是浏览器的跨源资源共享机制，用于控制一个源的页面能否读取另一个源的响应。它不是服务端之间通信的限制，而是浏览器安全策略。

- **简单请求**：满足方法和头部限制，例如 `GET`、`HEAD`、部分 `POST`，浏览器直接发请求，并根据响应头判断是否允许读取。
- **预检请求**：对复杂请求，浏览器先发送 `OPTIONS`，询问服务端是否允许该方法、请求头和来源。

关键响应头：

- `Access-Control-Allow-Origin`
- `Access-Control-Allow-Methods`
- `Access-Control-Allow-Headers`
- `Access-Control-Allow-Credentials`

### XSS、CSRF、SSRF 怎么区分？

| 攻击 | 核心 | 常见危害 | 防御 |
|---|---|---|---|
| XSS | 恶意脚本在用户浏览器执行 | 盗取 Token、冒充用户操作 | 输入校验、输出转义、CSP、HttpOnly |
| CSRF | 借用户登录态发起跨站请求 | 用户不知情地执行转账、修改资料 | SameSite、CSRF Token、Origin/Referer 校验 |
| SSRF | 诱导服务端访问攻击者指定地址 | 探测内网、访问云元数据 | URL 白名单、禁内网地址、响应隔离 |

## DNS、IP 与链路层

### DNS 完整解析流程是什么？

![DNS 递归查询流程](../Figures/Computer%20Network/DNS递归查询流程.svg)

浏览器访问域名时，通常会先查多级缓存：

1. 浏览器 DNS 缓存。
2. 操作系统缓存和 `hosts` 文件。
3. 本地 DNS 服务器缓存。
4. 本地 DNS 依次向根域名服务器、顶级域名服务器、权威域名服务器查询。

面试要点：客户端一般向本地 DNS 发起递归查询；本地 DNS 对外逐级查询更接近迭代查询；最终结果会按 TTL 缓存。

### DNS 为什么主要用 UDP？什么时候用 TCP？

DNS 查询默认使用 UDP，因为无需建立连接，开销小、响应快。以下场景会使用 TCP：

- 响应过大导致 UDP 截断。
- 区域传送，例如主从 DNS 同步。
- DNS over TCP、DoT 等特定配置。

现代 DNS 支持 EDNS，可以突破传统 512 字节限制，但 UDP 仍可能因为包过大、链路 MTU 或防火墙策略出现问题。

### DNS 劫持和 DNS 污染有什么区别？

- **DNS 劫持**：本地路由器、运营商、恶意软件或 DNS 服务商返回错误解析结果，把用户导向错误 IP。
- **DNS 污染**：攻击者向查询链路注入伪造 DNS 响应，使客户端或递归 DNS 缓存错误结果。

防护方式包括使用可信 DNS、DoH/DoT、DNSSEC、HTTPS 证书校验，以及监控域名解析变更。

### ARP 是什么？为什么会有 ARP 欺骗？

ARP 用于在同一局域网内根据 IP 查询 MAC 地址。主机发送广播：“谁是这个 IP？请告诉我你的 MAC。”目标主机单播回复自己的 MAC。

ARP 欺骗的根因是 ARP 缺少认证机制，主机可能接受伪造的 IP-MAC 映射，导致流量被中间人截获或网关不可达。

防护方式：

- 静态 ARP 绑定。
- 交换机开启 DHCP Snooping、Dynamic ARP Inspection。
- 使用 HTTPS、SSH 等端到端加密降低被监听后的危害。

### DHCP 获取 IP 的流程是什么？

DHCP 常用 DORA 四步：

1. `Discover`：客户端广播寻找 DHCP 服务器。
2. `Offer`：服务器提供可用 IP、网关、DNS、租期等配置。
3. `Request`：客户端选择一个 Offer 并广播确认。
4. `ACK`：服务器确认租约，客户端正式使用 IP。

DHCP 客户端通常使用 UDP 68 端口，服务端使用 UDP 67 端口。

### NAT 和 NAPT 有什么区别？

- **NAT**：只转换 IP 地址。
- **NAPT**：同时转换 IP 和端口，也就是常说的端口复用。多个内网主机可以共享一个公网 IP 访问外网。

NAPT 会维护转换表，例如 `192.168.1.10:50000 -> 公网IP:30001`。外部主机默认无法主动访问内网服务，因为没有对应转换表项，除非配置端口映射、UPnP、内网穿透等。

### IPv4 分片为什么不推荐？

IP 包超过链路 MTU 时可能被分片，但分片有明显问题：

- 任意一个分片丢失，整个 IP 数据报都无法重组。
- 重组只在目的主机进行，增加接收端压力。
- 分片可能被防火墙丢弃，也可能带来安全风险。

实际工程中常通过 Path MTU Discovery、合理设置 MSS、避免发送过大 UDP 包来减少分片。

## TCP 与 UDP

### TCP 为什么可靠？

TCP 的可靠性来自多种机制组合：

- 序列号保证有序重组。
- 确认号和 ACK 确认已收到数据。
- 超时重传、快速重传、SACK 处理丢包。
- 校验和发现传输错误。
- 滑动窗口实现流量控制。
- 拥塞控制保护网络不过载。
- 三次握手和四次挥手管理连接生命周期。

### TCP 粘包和拆包是什么？怎么解决？

TCP 是字节流协议，不保留应用层消息边界。发送端多次写入的数据，接收端可能一次读到；发送端一次写入的数据，接收端也可能分多次读到。这就是常说的粘包和拆包。

解决方案本质都是“定义应用层协议边界”：

- 固定长度消息。
- 分隔符，例如 `\r\n`。
- 消息头携带 body 长度，例如 HTTP 的 `Content-Length`。
- 使用成熟协议编码，例如 Protobuf、gRPC、WebSocket Frame。

### TCP 三次握手为什么不是两次？

主要原因是避免历史连接误建立，并确认双方收发能力和初始序列号。

- 两次握手时，服务端收到一个旧 SYN 后就可能进入已连接状态，浪费资源。
- 三次握手中，客户端最后一次 ACK 可以证明客户端收到了服务端的 SYN-ACK，双方都确认了对方的发送和接收能力。

### TCP 四次挥手为什么不是三次？

TCP 是全双工连接，双方的发送方向需要分别关闭。

- 主动关闭方发送 `FIN`，表示自己没有数据要发了。
- 被动关闭方先回 `ACK`，表示知道了。
- 被动关闭方可能还有数据没发完，等数据发完后再发送自己的 `FIN`。
- 主动关闭方回 `ACK`，连接进入 `TIME_WAIT`。

如果被动关闭方刚好没有数据要发，可以把 `ACK` 和 `FIN` 合并，看起来像三次，但逻辑上仍是四个动作。

### TIME_WAIT 的作用是什么？为什么要等 2MSL？

`TIME_WAIT` 主要有两个作用：

- 确保最后一个 ACK 能被对方收到。如果 ACK 丢失，对方会重发 FIN，主动关闭方还能再次 ACK。
- 让旧连接中的迟到报文在网络中自然消失，避免污染使用相同四元组的新连接。

等待 `2MSL` 是为了覆盖报文一个来回的最大生存时间。

### 大量 TIME_WAIT 怎么处理？

先判断是否真的有问题。`TIME_WAIT` 是正常 TCP 状态，不应一看到就盲目优化。

常见处理：

- 使用连接池或长连接，减少频繁建连断连。
- 服务端尽量让客户端主动关闭连接，减少服务端 `TIME_WAIT`。
- 调整内核参数需要谨慎，不能为了消除状态破坏协议语义。
- 排查是否有短连接风暴、健康检查过频、超时配置不合理。

### CLOSE_WAIT 过多说明什么？

`CLOSE_WAIT` 表示对端已经关闭连接，本机也已经收到 FIN 并回复 ACK，但本机应用还没有调用 `close()`。大量 `CLOSE_WAIT` 通常说明应用层没有正确释放连接，例如连接泄漏、线程阻塞、异常路径未关闭 socket。

### TCP 流量控制和拥塞控制有什么区别？

- **流量控制**：保护接收方，避免发送方发太快导致接收缓冲区被打满。核心是接收窗口 `rwnd`。
- **拥塞控制**：保护网络，避免网络链路和路由器过载。核心是拥塞窗口 `cwnd`。
- 实际发送窗口通常取 `min(rwnd, cwnd)`。

### TCP 拥塞控制有哪些阶段？

- **慢启动**：拥塞窗口指数增长，用于快速探测可用带宽。
- **拥塞避免**：达到阈值后线性增长，避免过快压垮网络。
- **快速重传**：收到多个重复 ACK 后，不等超时就重传可能丢失的段。
- **快速恢复**：丢包后降低窗口，但不一定回到最小值，尽量保持吞吐。

### UDP 真的不可靠吗？为什么还要用 UDP？

UDP 不保证可靠、有序、不重复，也没有拥塞控制和连接管理。但它简单、延迟低、报文边界清晰，适合：

- DNS、DHCP 等短请求。
- 音视频、直播、游戏等更关注实时性的场景。
- QUIC 这类在应用层自行实现可靠传输和拥塞控制的协议。

“UDP 不可靠”不是缺点的全部，更准确地说是“UDP 把可靠性选择权交给应用层”。

### QUIC 如何在 UDP 上实现可靠传输？

QUIC 自己实现了 TCP 中很多能力：

- Packet Number 用于丢包检测和确认。
- Stream ID + Offset 用于多路复用和流内有序重组。
- ACK Frame 表达接收情况。
- 拥塞控制和流量控制限制发送速率。
- TLS 1.3 内置加密，减少中间设备干扰。

与 TCP 不同，QUIC 的多个 Stream 更独立，一个流丢包通常不会阻塞其他流向应用层交付。

## WebSocket 与实时通信

### WebSocket 和 HTTP 有什么关系？

WebSocket 建连时依赖 HTTP Upgrade：

1. 客户端发送 HTTP 请求，带上 `Upgrade: websocket` 和 `Connection: Upgrade`。
2. 服务端返回 `101 Switching Protocols`。
3. 之后连接从 HTTP 请求-响应模型升级为 WebSocket 全双工通信。

WebSocket 适合聊天、游戏、协同编辑、实时行情等服务端需要主动推送的场景。

### WebSocket、SSE、轮询怎么选？

| 方案 | 特点 | 适用场景 |
|---|---|---|
| 短轮询 | 客户端定时请求 | 实现简单、实时性要求低 |
| 长轮询 | 请求挂起直到有数据或超时 | 兼容性好，但连接管理复杂 |
| SSE | 服务端到客户端单向推送，基于 HTTP | 通知流、日志流、股票价格 |
| WebSocket | 全双工长连接 | 聊天、游戏、协同编辑 |

如果只需要服务端单向推送，SSE 往往比 WebSocket 更简单；如果需要双向高频通信，优先 WebSocket。

## 网络排障

### `ping`、`traceroute`、`telnet/nc`、`curl` 分别排查什么？

- `ping`：基于 ICMP，检查网络层可达性和大致 RTT，但目标禁 ICMP 时可能失败。
- `traceroute` / `tracert`：观察路径上的路由跳点，定位在哪一跳开始异常。
- `telnet` / `nc`：检查目标 TCP 端口是否可连接。
- `curl -v`：检查 DNS、TCP、TLS、HTTP 状态码、响应头等应用层细节。

### 浏览器访问一个网站很慢，如何排查？

可以按链路分层排查：

1. **DNS**：域名解析是否慢，是否解析到错误 IP。
2. **TCP**：握手是否慢，是否丢包、重传、窗口过小。
3. **TLS**：证书链是否过长，是否握手失败或协议版本过旧。
4. **HTTP**：状态码、重定向次数、缓存是否命中、响应体是否过大。
5. **服务端**：应用耗时、数据库、下游 RPC、队列积压。
6. **前端渲染**：资源阻塞、JS 执行、图片过大、首屏渲染慢。

面试中可以补一句：先用浏览器 DevTools 的 Network 面板看瀑布图，再用 `curl -v`、`dig/nslookup`、`ping`、`traceroute`、抓包工具逐层验证。

### 502、503、504 怎么区分？

- `502 Bad Gateway`：网关或代理收到了上游的错误响应，例如 Nginx 访问后端失败。
- `503 Service Unavailable`：服务暂时不可用，可能是过载、维护、限流。
- `504 Gateway Timeout`：网关等待上游响应超时。

常见排查方向：反向代理配置、上游服务存活、端口连通性、超时时间、负载均衡健康检查、应用日志。

### 线上偶发连接超时，可能有哪些原因？

- DNS 解析慢或解析异常。
- TCP 握手丢包、SYN backlog 满、服务端连接数耗尽。
- 防火墙、NAT、负载均衡连接跟踪表满。
- 服务端线程池、连接池、数据库池耗尽。
- GC、CPU 飙高、磁盘 IO 卡顿。
- 客户端超时时间设置过短，或者没有连接复用。

答题时最好先说“按 DNS → TCP → TLS → HTTP → 应用依赖分层定位”，再展开可能原因。
