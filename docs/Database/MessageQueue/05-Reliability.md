# 🧩 消息可靠性模式

## 本地消息表是什么？适合解决什么问题？

本地消息表是把业务数据和待发送消息放在同一个数据库事务中提交。事务成功后，后台任务扫描未发送消息并投递到 MQ，发送成功再把消息状态改为已发送。

它解决的是“业务事务成功但消息没发出去”的问题。缺点是依赖数据库轮询，实时性一般，消息表也需要清理、分片和监控。

## Outbox 模式和本地消息表有什么关系？

Outbox 模式本质上也是把事件作为业务数据库的一部分写入，只是更强调事件流和 CDC。业务服务在本地事务中写业务表和 outbox 表，之后由投递器或 binlog / CDC 组件把 outbox 事件发送到消息系统。

它的优势是业务事务和事件产生在同一数据库边界内，避免双写不一致。消费端仍然要处理重复投递，因为投递器可能在发送成功但标记状态前宕机。

## MQ 如何配合数据库事务？

最常见方案有三类。

- **本地消息表 / Outbox** ：业务库事务内写消息记录，异步投递。
- **事务消息** ：先发半消息，本地事务完成后提交消息。
- **最终一致补偿** ：先完成主流程，失败通过重试、对账、人工介入补偿。

真正强一致的两阶段提交成本高、耦合重，互联网业务更多使用最终一致。回答时要结合业务容忍度：支付扣款、库存扣减、通知短信，对一致性和延迟的要求不同。

## 如何设计消费者幂等表？

消费者幂等表通常包含消息 ID、业务主键、消费状态、处理时间、重试次数等字段，并对消息 ID 或业务唯一键建立唯一索引。

处理流程是：先尝试插入幂等记录，插入失败说明处理过；插入成功后执行业务逻辑，并在同一事务中更新业务状态和幂等状态。这样即使 MQ 重投，重复消息也不会重复修改业务结果。

如果业务操作本身具备状态机约束，例如订单只能从 `PAID` 流转到 `SHIPPED`，也可以用状态条件更新实现幂等。

## 死信队列应该怎么用？

死信队列用于承接多次重试仍失败、过期、被拒绝且不重新入队的消息。它不是垃圾桶，而是异常处理入口。

比较完整的死信处理流程包括告警、记录失败原因、提供查询和重放工具、区分可自动恢复和需要人工介入的问题。重放死信前要确认业务幂等，否则可能造成二次事故。

## 如何回答“消息队列能不能保证 exactly-once”？

要先拆边界。单个 MQ 内部可能提供幂等写入、事务写入、已提交读取等能力，但端到端 exactly-once 涉及生产者、Broker、消费者、数据库、外部接口多个系统。

在真实业务里，更常见的答案是：MQ 提供至少一次投递，业务通过幂等消费、事务边界和补偿机制实现“最终结果等效一次”。如果面试官继续追问 Kafka exactly-once，要说明它主要覆盖 Kafka 读写链路，不能自动覆盖外部数据库。
