# 🚀 RocketMQ

## RocketMQ 事务消息的流程是什么？

RocketMQ 事务消息通常分三步：生产者先发送半消息，Broker 暂不投递给消费者；生产者执行本地事务；生产者根据本地事务结果提交或回滚半消息。

如果生产者迟迟没有返回最终状态，Broker 会回查生产者，由生产者根据本地事务表判断应该提交还是回滚。这个机制适合解决“本地事务成功，但发送消息结果不确定”的问题。

注意事务消息不等于分布式事务万能解。消费者处理仍可能失败或重复，消费端仍需要幂等和补偿。

## RocketMQ 顺序消息如何实现？

RocketMQ 的顺序消息依赖把同一业务实体的消息发送到同一个 MessageQueue，并由消费者按队列顺序消费。例如同一订单的创建、支付、发货事件使用订单 ID 做队列选择。

顺序消息的代价是并行度下降。如果某个队列里有慢消息或失败重试，后续同队列消息可能被阻塞。因此它适合局部顺序，不适合随意要求全局顺序。

## RocketMQ 延迟消息有什么特点？

RocketMQ 支持延迟消息，适合订单超时关闭、预约提醒、重试退避等场景。不同版本的延迟能力有所差异，有的版本是固定延迟等级，有的版本支持更灵活的定时 / 延迟消息。

答题时要说清：延迟消息不是精准定时器。Broker 调度、负载、消费者处理能力都会影响最终触达时间，业务上要允许一定延迟误差。

## RocketMQ 重试和死信队列如何理解？

消费者消费失败后，RocketMQ 会按策略进行重试。达到最大重试次数后，消息会进入死信队列，需要人工排查或专门的补偿任务处理。

线上不要无限重试。异常消息如果反复失败，会消耗消费能力并造成积压。更好的方式是记录失败原因、控制重试次数、告警，并把不可自动恢复的问题转入死信处理流程。

## RocketMQ 的消费进度如何管理？

消费进度表示消费者已经处理到哪个位置。集群消费模式下，进度通常由 Broker 侧维护；广播消费模式下，每个消费者都要各自消费一份消息，进度语义不同。

排查“为什么消息又被消费了”时，要看消费模式、offset 提交时机、消费者重启、重平衡、处理失败重试等因素。业务上仍然要按唯一消息 ID 或业务主键做幂等。
