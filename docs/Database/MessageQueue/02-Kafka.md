# 🟫 Kafka

## Kafka 为什么吞吐高？

Kafka 的高吞吐来自多个设计叠加：顺序写磁盘、页缓存、批量发送、零拷贝、分区并行和拉模式消费。它不是因为“不落盘”才快，恰恰相反，Kafka 通过顺序追加日志把磁盘写入变得高效。

生产者可以把多条消息批量压缩后发送，Broker 按分区追加写日志文件，消费者按 offset 顺序拉取。读取热点数据时，操作系统页缓存能减少真实磁盘 I/O。

## Kafka 的 ack 参数如何影响可靠性？

生产者 `acks` 决定收到多少确认才认为发送成功。

- `acks=0` ：不等确认，吞吐高但最容易丢消息。
- `acks=1` ：leader 写入成功就确认，如果 leader 宕机且 follower 未同步，仍可能丢。
- `acks=all` ：leader 等待 ISR 中副本确认，可靠性更高，通常还要配合 `min.insync.replicas`。

生产环境如果追求可靠性，常见组合是 `acks=all`、开启重试、配置合适的 `min.insync.replicas`，并关注 ISR 缩小告警。

## Kafka 幂等生产者解决什么问题？

幂等生产者用于解决生产者重试导致的分区内重复写入问题。Broker 会根据 producer id、分区和序列号识别重复消息，使同一个生产者会话内的重试写入不重复落盘。

它保证的是单分区、单会话维度的幂等写入，不等于完整业务幂等。消费者仍可能重复消费，跨系统写数据库也仍需要业务幂等。

## Kafka 事务能实现什么级别的一致性？

Kafka 事务可以把多个分区的消息写入和消费 offset 提交放进同一个事务中，让下游以 `read_committed` 模式只读到已提交事务消息。这是 Kafka exactly-once 语义的重要基础。

但它的边界在 Kafka 内部。如果消费者处理消息后还要写 MySQL、调用外部接口，Kafka 事务不能自动保证外部系统也 exactly-once。此时仍需要本地事务、事务消息、Outbox、幂等消费等设计。

## Kafka offset 什么时候提交比较安全？

自动提交简单但有风险：消息刚拉取还没处理完，offset 已经提交，消费者宕机后这批消息不会再消费，造成丢失。

更稳妥的是处理成功后手动提交 offset。如果先处理后提交，宕机时可能重复消费；如果先提交后处理，宕机时可能丢消息。多数业务会选择“至少一次 + 幂等消费”。

## Kafka 如何保证消息顺序？

Kafka 只能天然保证单分区内有序，不能保证整个 topic 全局有序。要让同一业务实体有序，可以用订单 ID、用户 ID 等作为 key，让相关消息进入同一个分区。

代价是热点 key 会造成分区倾斜，且单分区只能被同一个消费组内的一个消费者实例消费，吞吐受限。全局严格有序通常意味着只能用一个分区，性能会明显下降。

## consumer group 和 partition 的关系是什么？

同一个 consumer group 内，一个 partition 同一时刻只能分配给一个消费者实例；一个消费者可以消费多个 partition。消费者数量超过 partition 数时，多出来的消费者会空闲。

这解释了为什么扩容消费者不一定提升吞吐：如果 topic 只有 4 个分区，消费组扩到 10 个实例，最多也只有 4 个实例真正消费。
